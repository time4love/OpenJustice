## 4. THE FONTS — why there are FOUR files, measured rather than assumed

`document.fonts.check` is not the first evidence; the `cmap` is. Both seats decoded every face independently (a woff2 table-directory parse, a
brotli decompress of the font stream, then `cmap` and `fvar` read by hand — no font library), and the figures agree exactly:

| face | bytes | codepoints | **digits 0–9** | Hebrew 0590–05FF | presentation FB1D–FB4F | `fvar` wght |
|---|---|---|---|---|---|---|
| `frank-ruhl-libre-hebrew-wght-normal.woff2` | 18,748 | 109 | **0** | 53 | 44 | 300–900 |
| `frank-ruhl-libre-latin-wght-normal.woff2` | 44,332 | 222 | 10 | 0 | 0 | 300–900 |
| `heebo-hebrew-wght-normal.woff2` | 12,036 | 108 | **0** | 50 | 45 | 100–900 |
| `heebo-latin-wght-normal.woff2` | 30,116 | 219 | 10 | 0 | 0 | 100–900 |

**Both Hebrew subsets carry ZERO digits, and Hebrew headings are full of them** — „בצילום מ־28.6.2022”, version dates, chunk counts. Without
the Latin subsets, every digit inside a Hebrew claim would have fallen to the system face mid-word. **DEV added the fact REVIEW had missed:**
both Hebrew subsets DO map the maqaf U+05BE and the geresh U+05F3, so „…מ־{date}” and „בידי המחבר/ת” render whole from face 1 and only their
DIGITS would have dropped out — a narrower defect than "Hebrew breaks", and exactly as serious.

**The retired August file was replaced at zero cost, measured:** its coverage is identical to the Fontsource Hebrew subset codepoint for
codepoint (109 · 53 · 44 · 0 digits), decompressing to 39,053 bytes against 39,074 — the 21-byte difference is a `prep` table the newer build
carries. An unprovenanced binary left the repo for a versioned one with a licence (both families OFL-1.1; neither declares a Reserved Font
Name, so no alias was needed).

**`adjustFontFallback: false` on all four calls, and this is the trap the loader's own source revealed.** `postcss-next-font.js` emits the
variable as `[family, '<family> Fallback', ...fallbackFonts]`, and `'<family> Fallback'` is a generated `@font-face` whose `src` is
`local("Arial")` (`get-fallback-metrics-from-font-file.js`: `DEFAULT_SANS_SERIF_FONT.name = 'Arial'`). **That is a real, matchable family with
digits sitting mid-chain**, so composing `var(--hebrew), var(--latin)` with the default left on would have defeated the four files entirely.
**Nor is the serif default an escape** — the only other option is `Times New Roman`, which also has digits. Confirmed on the deployed page:
`--font-serif` = `"frankHebrew","frankLatin","Times New Roman",serif`, `--font-sans` = `"heeboHebrew","heeboLatin",system-ui,sans-serif` —
**one family per variable, no Fallback family, no Arial anywhere.**

**`--font-mono` is a system stack** (`ui-monospace, SFMono-Regular, Menlo, monospace`) and no fifth file landed: the step deletes Geist Mono,
and the values it carried — hashes, the registry index, the citation tokens — are Latin and digits only.

**Preloads:** the SERVED HTML carries **no font preload at all**; all four are client-injected after hydration (`initiatorType: "link"`). The
~105 KB per route is real and is NOT on the critical path. `preload: false` on the two Latin subsets remains the lever, undecided, now with the
mechanism measured rather than assumed.

## 6. WHAT THE BROWSER FOUND THAT THE SUITE COULD NOT — five defects, and this is the step's real record

**jsdom is handed a tree, never markup, and has no layout engine.** It cannot see a splitter drag, a pane resize, a drawer open, a real focus
order, a font FILE load, per-glyph fallback, or any media query. Almost everything UI-4b lands is in that set — which is why the local run and
the staging exercise carry this step, not the suite.

**Three found on `localhost`, all fixed and re-measured:**
1. **The collapsed sidebar could not be re-opened.** Collapsed, the sidebar was 24 px while its expand control was 44 px at x=8, and
   `document.elementFromPoint` at the control's centre returned `SECTION` — the page behind it. **The researcher caught this one by watching.**
   It now collapses to a rail of one touch target holding only that control; re-measured, the toggle round-trips 268 → 44 → 268.
2. **The phone drawer opened on the RIGHT.** `inset-inline-start` resolves to the right in a Hebrew document, while board E draws it left.
   Changed to a physical `left: 0` — the shell is left-anchored at every width and in both locales, the same reason `.shell` is `direction: ltr`.
3. **The splitter moved one step per key burst** — four presses moved 16 px, not 64 — because every press computed from the same prop the
   render had closed over.

**Two found on STAGING, and one of them is open:**

### F8 — the serif is self-hosted, correct, and APPLIED TO NOTHING
On the published thesis page, `document.fonts.check` is **FALSE** for both Frank Ruhl Libre faces and both report `unloaded`. Measured over
`main`: **182 elements resolve to the sans, 7 to the mono, ZERO to the serif**; outside `:root` there is **not one CSS rule that applies
`--font-serif`**, and `frankHebrew` appears in no page's served HTML. **The face is never requested, which is why it never loads.** §1.8's
central idea — *Frank Ruhl Libre for the researcher's words and headings, Heebo for the chrome* — and the reason four files landed, are inert.
**Nothing held it:** `fonts-are-local` asserts the DECLARATIONS and the chain's ORDER, never that a glyph rendered, so it is green over a page
where the serif renders nothing. **The same shape as R56's F1 — a declaration asserting something the page does not do.**
**It is not a defect of this step's code**: every page that would apply the serif is KEEP here. **Ruled by the researcher, option (b):** §9
:1107's owed reading MOVES to UI-5, amended in place, and this doc records that the faces are in the tree, self-hosted and correct, and that
**no glyph has yet rendered in one**. Both HEEBO faces do load and check true.
