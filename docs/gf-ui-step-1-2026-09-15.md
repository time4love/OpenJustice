## 3. What the reading found before the code, and the rulings

- **next-intl, use-intl, intl-messageformat and `@formatjs/*` ship ES modules only**, and `next/jest` transforms nothing under
  `node_modules` but its own list; a custom `transformIgnorePatterns` entry can only ignore more. So `jest.config.ts` rewrites
  next/jest's first pattern to carry the eight packages, and refuses loudly if next/jest ever writes that pattern differently.
  `next.config.ts` (`transpilePackages`) was not the door taken — it is KEEP and would change the production build.
- **`next-intl/server` outside the `react-server` condition throws** on every function. `StagingBanner`, a Server Component, is
  rendered as written by awaiting it, with `next-intl/server` replaced in `test/setup.ts` by one stand-in built on `createTranslator`
  over the real messages (ruled: keep `StagingBanner`, the component the plan names, rather than substitute a client component).
- **`next/jest({ dir })` loads `.env.test.local`, `.env.test` and `.env`** into the process the workers inherit. Kept (it gives the
  `@/*` paths); a case calls `@next/env`'s `loadEnvConfig` on the workspace and asserts it loads no file.
- **The name scan reads `.ts` as well as `.tsx`** (ruled; design A5 :1086 "no user-facing string" over plan :111's narrower glob),
  matches the design's two words in any case and whitespace, and excludes comments by reading literal nodes only — a JSX comment's
  text belongs to the closing brace's trivia, which a comment-finding pass missed on its first measurement.
- **The hyphenated form is not the term** (ruled): `src/components/SiteFooter.tsx:27` links the repository path
  `…/apps/glass-fortress`, and `src/lib/api.ts:127` shows the Railway MCP host `glass-fortress-backend-production…` on
  `/researchers`. The public URL will be on the site's own domain at launch; until then the Railway URL may show. UI-9 replaces the
  constant with the deployment's origin.
- **A missing message throws** on both render paths (review finding): without an `onError`, next-intl renders `namespace.key` as a
  text node, which a later instrument reading the DOM would pass over.

## 5. What the sketch predicted that did not happen

- `ts-node` over the frontend `tsconfig` was predicted to fail with TS5095 (`bundler` resolution under CommonJS). It did not; the first
  failure was TS2345 — next/jest's parameter type comes from the root's jest 29 types. The config is typed by next/jest's own
  parameter and carries no loader pragmas; on CI's node 22 it loaded with no parse failure in the job's log (whether natively
  or through the ts-node fallback, the log does not say).
- The ESM failure's wording under jest 30 is "Must use import to load ES Module", not "Cannot use import statement outside a module".
- `jest-environment-jsdom` installed at the root, not under the frontend.
- A translation stand-in returning the key reddened the two `StagingBanner` cases, not the wrapper case, which renders through the
  client provider.
- The install warned EBADENGINE three times on node 20: the GF backend's own `engines >=22` (now in the lockfile), and two packages
  under `oidc-provider`. CI runs node 22.
